# Skill distribution: dotfiles is the source of truth

Decided 2026-08-22. This is the workflow, not a proposal.

Companion: [worktree-workflow.md](worktree-workflow.md) applies the same discipline to workspaces, and carries the combined task list for what is still unbuilt across both.

## The rule

**`~/dotfiles` is the single source of truth for skills.**
It is portable: drop it on any machine, any OS, and use it. Some pieces will not work everywhere, and that is accepted.

**A skill copied into a project is immutable.**
The project never edits it. If a skill needs to change, you go upstream to dotfiles, change it there, bump it, and let the project pick the change up on its next session.

## Why this is enforced structurally rather than asked for politely

Today the enforcement is a sign on the door: a read-only notice copy-pasted into all 42 `SKILL.md` files, asking agents not to edit the thing they are currently looking at.
`skill-update.sh` replaces a skill's directory rather than merging into it, so a local edit is destroyed by the next update with no conflict and no warning. The notice is the only thing standing between an agent and that.

From now on the directory is gitignored instead. A local edit cannot be committed, so there is no path to changing a skill except upstream.

That is a lock rather than a sign. An agent can still edit its copy, but the edit was never going to be committed, so nothing is lost when the next update overwrites it.

## The three moving parts

### 1. The project side: the skills directory is gitignored

`project-scaffold`'s gitignore template ignores `<project>/.claude/skills/` for every project scaffolded from now on.

**Consequence worth planning for:** a fresh clone of a project then has **no skills at all** until the session-start check runs.
The check therefore stops being "compare and maybe update" and becomes "install if absent, else compare".
That is a real behavioural change to the script, not a config change, and it is in scope whenever this gets built.

`.claude/scaffold.json` records which skill version the vendored copies came from. If the directory beside it is ignored, that record either has to survive independently or be regenerated by the same install step.

### 2. The session side: check, then swap

A fresh session on any project:

1. Fetches the published registry from GitHub.
2. Compares it against the installed `version:` lines.
3. Does nothing, or swaps the stale skill out using the update script.

Unchanged in spirit from what exists today. The difference is that it now also installs from cold.

### 3. The dotfiles side: CI/CD owns the version and the registry

Version bumping and registry regeneration move into GitHub Actions on `dotfiles`.
**This is dotfiles-side only. It changes nothing about how a project behaves.**

A pull request carries _intent_ rather than a number - a commit trailer or a PR label naming the skill and the bump level. On merge to `main`, the workflow runs the bump, regenerates `registry.json`, and commits.

## The problem this solves

A version number is a claim about **ordering**, but it was being allocated at **author time** from a snapshot of `main` that goes stale the moment anyone else merges. Ordering is not knowable until merge, so allocating it earlier is guaranteed to be wrong sometimes.

It went wrong immediately and in the open:

| PR  | What it did                               | Version claimed for `project-scaffold` |
| --- | ----------------------------------------- | -------------------------------------- |
| #42 | Update skills from GitHub, not a checkout | 1.2.0                                  |
| #41 | Runbook rule in the `CLAUDE.md` template  | 1.2.0                                  |

Two different content hashes, both calling themselves `1.2.0`, both correct at the moment they were written.
Git caught it only because the two branches touched the same two lines. **The collision was semantic and the mechanism that detected it was textual** - that is luck, not design.

A second, related failure: `registry.json` is one file listing all 42 skills, so _every_ skill bump touches it. It is a guaranteed conflict point between any two concurrent skill PRs, related or not. Allocating versions at merge time removes it from pull requests entirely, so the conflict cannot happen.

#42 also shows the blast radius: it rewrote the read-only notice in every `SKILL.md`, which under the current rule forced a bump on all 42 skills and invalidated every in-flight branch at once.

## Still open, not designed

**A skill local to one project that still needs version control.**
Current thinking: state that skill's instructions in the project's own `CLAUDE.md` rather than vendoring a directory for it. Not designed yet, deliberately.

## What this replaces

Rule 16 in root `CLAUDE.md` currently requires any PR touching `claude/skills/<name>/` to bump that skill and ship the regenerated registry in the same PR.
That rule stays true in intent, but the _actor_ changes from the author to the pipeline. It also needs a carve-out, or removal, for changes that touch only shared boilerplate.

Note also that `skill-version.sh verify` is the gate for Rule 16 today, and it only ever runs locally. Nothing enforces the rule at merge time - it holds because whoever is driving remembers to run it. Moving it into CI closes that gap as a side effect.
